# Stripe Service

⚠️ **The name is now narrower than the service.** A second acquirer (Revolut
Merchant) is mirrored here alongside Stripe. The rename to `payment-service` is
deliberately LAST — it is a deploy operation (repo, env var names, hostname,
registry entry), not a refactor, and doing it before the consumer migration
would break every caller's env for no gain. See issue #122 for the sequencing.

Thin Stripe wrapper. Mirrors a subset of Stripe API objects (customers, checkout
sessions, payment intents, billing portal sessions) under Stripe-native routes
and DB tables. Internal-only HTTP API consumed by other Distribute services
(billing-service, future subscription-service). The service has no business
knowledge of its callers — all reload/dedupe logic lives in clients.

## Architecture
- **src/schemas.ts** — Zod schemas + OpenAPI path registration (single source of truth)
- **src/middleware/serviceAuth.ts** — X-API-Key authentication
- **src/middleware/identityHeaders.ts** — Requires x-org-id + x-user-id; logs optional context headers
- **src/middleware/callLog.ts** — Appends to api_call_log on every authenticated request
- **src/lib/stripe-client.ts** — Per-org Stripe SDK factory + webhook verifier
- **src/lib/key-client.ts** — Key-service HTTP client
- **src/lib/resolve-stripe-key.ts** — Resolves Stripe key from key-service via orgId + userId
- **src/lib/request-context.ts** — Builds per-request Stripe client + identity context
- **src/lib/event-processor.ts** — Bronze (events) ingestion + silver (customers/payment_intents/checkout_sessions) projection. `processEvent()` inserts webhook/poll events into bronze, then calls `projectSilverFromBronze(objectId, orgId)` which reads `MAX(events.created_stripe)` for that object_id and upserts silver from the latest payload. `recordApiSnapshot(obj, kind, orgId)` is the entry point for API-response paths — inserts a synthetic `api_snapshot.<kind>` event into bronze, then projects. Routing to a silver table is done by `detectObjectKind(obj, objectId)` on the payload's own `object` field (see the routing key pattern below) — never by the object id's prefix. `repairAllSilverFromBronze()` runs at boot to re-project every distinct object_id (idempotent, bounded by event-count). Also dispatches post-mirror side-effects (default-PM promotion, charge-level refund mirroring, Stripe-fee declaration) for real Stripe events only — synthetic events never trigger side-effects.
- **src/lib/mirror-charge-refunds.ts** — Side-effect fired on `charge.refunded` / `charge.refund.updated`: lists `refunds.list({ charge })` off Stripe and snapshots each Refund into the mirror. Covers the case where the only event Stripe delivers carries a Charge (whose `refunds` sub-list is not expanded), so refund mirroring never depends on which event arrives.
- **src/lib/invoice-provenance.ts** — `paymentIntentIdFromInvoice(invoice)` (reads `invoice.payments[].payment.payment_intent`, falls back to the legacy top-level `payment_intent` field) + `paymentIntentProvenance(invoiceMetadata, invoiceId)`. Used by the off-session invoice route and the historical backfill script to carry caller provenance from an Invoice onto the PaymentIntent consumers read.
- **src/lib/promote-default-pm.ts** — Side-effect fired on `checkout.session.completed` and `setup_intent.succeeded`: if the customer has no `invoice_settings.default_payment_method` yet, promote the PM used in the session/intent so off_session reloads + `has_payment_method` work going forward. Idempotent.
- **src/lib/declare-fees.ts** — Side-effect fired on `charge.succeeded`, `charge.refunded`, `charge.dispute.created`, `payout.failed`: looks up the Stripe `balance_transaction.fee`, resolves the org via the customers mirror, reads the org's keySource from key-service, then declares the fee as a cost on a synthetic platform-run in runs-service. Idempotent per Stripe `balance_transaction.id` via the runs-service `idempotencyKey` field.
- **src/lib/notify-payment-method-removed.ts** — Side-effect fired on `payment_method.detached`: resolves the org the payment method was removed from, counts the customer's remaining chargeable cards, and sends a STAFF notification through transactional-email-service. Mirrors nothing. Swallows every failure (see the key pattern below).
- **src/lib/transactional-email-client.ts** — HTTP client for transactional-email-service. `deployEmailTemplates()` (idempotent `PUT /platform-templates`, called from `index.ts` inside the `app.listen()` callback, never awaited) + `sendStaffEmail()` (`POST /platform-send`). Owns the `payment_method_removed` template and the frozen event key. **Both calls take the user-less routes, never `/templates` and `/send`.** Those two are behind `requireIdentityHeaders` and 400 without an `x-user-id` this caller does not have — the customer removed the card in Stripe's own portal, so nobody of ours is on the request. `/platform-send` is `requireOrgIdOnly` (real org, no user) and `/platform-templates` is `x-api-key`-only (boot has no org, no user and no run, so it sends none). **Never satisfy those guards with a zero-uuid placeholder** — that is the workaround removed in #77 and the reason the user-less path was built. Prod proved the point on 2026-08-01: the identity-guarded routes returned `400 Missing required headers` and the feature shipped mute.
- **src/lib/runs-client.ts** — HTTP client for runs-service. `createPlatformRun`, `addPlatformRunCost`, `updatePlatformRunStatus`. Used exclusively by the fee declaration side-effect.
- **src/lib/event-poller.ts** — 5-min background poll of `GET /v1/events` from Stripe (webhook-loss recovery)
- **src/lib/historical-backfill.ts** — Boot-time full-history back-fill of every mirrored table (customers, payment_intents, checkout_sessions, customer_balance_transactions) via Stripe object-list APIs (events.list useless beyond 30-day retention)
- **src/routes/** — `customers.ts`, `internal.ts` (all `/internal/*` server-to-server routes: org teardown + user-less org-scoped balance reads), `checkout-sessions.ts`, `payment-intents.ts`, `payment-methods.ts`, `billing-portal-sessions.ts`, `public-stats.ts`, `webhooks.ts`, `health.ts`
- **src/db/schema.ts** — Drizzle table definitions (Stripe-shape mirror)
- **scripts/generate-openapi.ts** — OpenAPI spec generator

## Routes

`/v1/*` = auth'd (X-API-Key + identity headers). `/internal/*` = auth'd (X-API-Key only, NO identity headers — server-to-server, org keyed off the path). `/public/*` = no auth, cross-org. `/health`, `/openapi.json` = public utility.

```
POST   /v1/customers                       — create (idempotent per org; attaches user email+name from client-service)
GET    /v1/customers/:id                   — retrieve (DB-first, Stripe fallback)
POST   /v1/customers/:id                   — update
GET    /v1/customers                       — list (DB-only)
DELETE /internal/customers/by-org/:orgId   — org teardown: delete Stripe customer online + tombstone mirror (idempotent)
GET    /internal/customers/by-org/:orgId        — user-less: org's customer raw_json (DB mirror), 404 if none
GET    /internal/customers/by-org/:orgId/all    — user-less: EVERY customer mirrored for the org, as a Stripe list
POST   /internal/customers/:id/metadata         — user-less: rewrite a customer's Stripe metadata (platform key), re-mirrors immediately
GET    /internal/payment_intents/by-org/:orgId  — user-less: org's PIs as Stripe list (DB mirror, no limit) + per-PI amount_refunded / amount_disputed_lost / amount_returned
GET    /internal/payment_summary/by-org/:orgId  — user-less: per-currency amount_received / amount_returned / amount_net ACROSS BOTH ACQUIRERS (DB mirror); ?as_of=<unix seconds> bounds payments AND returns to before that instant
GET    /internal/acquirer/by-org/:orgId         — user-less: which acquirer charges this org (absent = stripe)
PUT    /internal/acquirer/by-org/:orgId         — user-less: pin an org to an acquirer; creates its Revolut customer when needed
POST   /internal/charges/by-org/:orgId          — user-less: charge an org off-session, vendor-neutral result; 409 for a Stripe org (use the invoice route)
GET    /internal/payment_methods/by-org/:orgId  — user-less: org customer's PMs (live Stripe, platform key); ?type=card
POST   /internal/invoices/by-org/:orgId          — user-less: create + pay an OFF-SESSION invoice for the org's customer (finalized + paid Stripe invoice); idempotent per Idempotency-Key header
POST  /v1/checkout/sessions               — create (line_items required for mode payment/subscription; forbidden for mode setup)
GET   /v1/checkout/sessions/:id           — retrieve (DB-first, Stripe fallback)
GET   /v1/checkout/sessions               — list (DB-only)
POST  /v1/payment_intents                 — create
GET   /v1/payment_intents/:id             — retrieve (DB-first, Stripe fallback)
GET   /v1/payment_intents                 — list (DB-only) — used by callers to check in-flight reloads
GET   /v1/payment_methods?customer=&type= — live Stripe passthrough (no mirror); 404s when customer not in caller's org
POST  /v1/billing_portal/sessions         — create (no DB persistence; single-use URL)
POST  /v1/webhooks                        — Stripe webhook handler (signature-verified)
GET   /public/stats/billing               — cross-org aggregate Stripe money movement (no auth): gross paid + returned + net, all-time and per month/week
```

## Key patterns

- **Bronze/silver — silver is projected from bronze, never written directly.** The `events` table is bronze (append-only, full Stripe-event payload as `jsonb`, idempotent insert via `ON CONFLICT (id) DO NOTHING`). The `customers`, `payment_intents`, and `checkout_sessions` tables are silver — typed projections of bronze. The contract: any code that needs to write silver MUST go through `projectSilverFromBronze(objectId, orgId)` (which reads `MAX(events.created_stripe)` per object_id) or `recordApiSnapshot(obj, kind, orgId)` (which inserts a synthetic `api_snapshot.<kind>` bronze event with `created_stripe = floor(Date.now()/1000)` then projects). The `upsertCustomer` / `upsertPaymentIntent` / `upsertCheckoutSession` helpers in `event-processor.ts` are exported only for tests — production callers using them directly bypass the race guarantee. **Why:** Stripe webhook delivery order is not guaranteed. Pre-projection, `ON CONFLICT DO UPDATE` was last-write-wins, so an older `payment_intent.created` snapshot arriving after a newer `payment_intent.succeeded` would clobber silver back to `requires_payment_method`. This silently broke billing-service's `sumSucceededTopupsForCustomer` and triggered runaway reload cascades (DIS-70). Projection ordered by `events.created_stripe DESC, received_at DESC` eliminates the race by construction — Stripe `event.created` is monotonic per object across state transitions. Synthetic api_snapshot events use server time, so they dominate any past webhook for the same object; later real webhooks with higher `event.created` win automatically.
- **Stripe-shape passthrough.** Request bodies are validated with `.passthrough()` Zod schemas and forwarded verbatim to the Stripe SDK. Responses are the unmodified Stripe object. No custom request/response naming. **If a Stripe object does NOT have a corresponding Stripe API endpoint, do NOT invent a convenience wrapper here** — direct the caller to read the field off the parent Stripe-API endpoint we already mirror (e.g. `customer.balance` and `customer.invoice_settings.default_payment_method` read from `GET /v1/customers/:id`, not from `/v1/customers/balance` or `/v1/customers/has-payment-method`). Convenience flatteners with snake_case wrappers (`balance_cents` as string, flattened status enums, etc.) violate this rule.
- **1:1 org ↔ Stripe customer.** Each org has exactly one Stripe customer. Org-implicit reads (e.g. `GET /v1/balance_transactions`) resolve `customers WHERE org_id = $1 ORDER BY created_stripe DESC LIMIT 1`; 404 if no customer. Callers (billing-service) do NOT store `cus_xxx` — stripe-service is the source of truth for the mapping.
- **`POST /v1/customers` is idempotent per org — enforces the 1:1 invariant server-side.** Before creating, it resolves the org's existing mirrored customer (`customers WHERE org_id = $1 ORDER BY synced_at DESC LIMIT 1`); if one exists it returns it (no Stripe create). This kills duplicate Stripe customers from caller retries / races / multiple account-setup paths — billing's own `billing_accounts` guard was the only protection before, so any hiccup there minted a second `cus_…`. The create is now retry-safe, which is what makes the fail-loud email resolution below acceptable.
- **`POST /v1/customers` attaches the user's email + name from client-service.** stripe-service has no email of its own (same as it has no Stripe key of its own — resolved from key-service). Callers (billing-service `ensureCustomer`) POST an **empty body** `{}`, so the Stripe customer was born with no email. The POST now resolves `{email, firstName, lastName}` from client-service `GET /internal/users/:userId` (keyed off the `x-user-id` it already receives) via `src/lib/client-service-client.ts`, and stamps them — **only when the caller didn't supply an email** (caller-supplied values win; callers that already have an email skip the client-service hop). Existing emailless customers are **backfilled on the idempotent-return path** (`customers.update` with the resolved email). **Fail-loud:** an infra failure (network/5xx) propagates → 5xx → caller retries (safe, the create is idempotent). A 404 (no such user on record) is NOT a failure — it means there's genuinely no email to attach, so the customer is created without one rather than blocking the org's billing setup. Keeping email-resolution server-side fixes it transparently for every caller (billing today, future subscription-service) instead of each caller re-implementing it.
- **Public routes.** `/public/*` bypasses `serviceAuth` and `requireIdentityHeaders` middleware. Reserved for cross-org domain aggregates (stats, status pages). Not for Stripe-shape endpoints — those live under `/v1/`. Adding a new `/public/*` route is a deliberate architectural choice; reject the request unless the data is genuinely cross-org and non-sensitive.
- **Internal routes.** `/internal/*` keeps `serviceAuth` (X-API-Key mandatory) but is exempt from `requireIdentityHeaders` (the exemption is in `identityHeaders.ts`, NOT in `serviceAuth.ts` — never weaken the key check). Reserved for server-to-server platform operations where the caller has no end-user identity, the org is keyed off the path/body, and Stripe access (when needed) uses the **platform key** (`getPlatformStripe()`, single-account model) — there is no end-user to resolve a per-org key against. Examples: org teardown (`DELETE …/by-org/:orgId`) and the user-less org-scoped balance reads (`GET …/by-org/:orgId` for customers / payment_intents / payment_methods). **Belongs under `/v1/` instead, NOT `/internal/`:** any Stripe-shape read/write that needs **per-org, per-user key resolution** (`resolveStripeKey(orgId, userId)` — BYOK vs platform chosen per the user's org) or that stamps end-user identity. The discriminator is the KEY-RESOLUTION path (platform vs per-user), not "is it Stripe-shape". The user-less balance reads exist because billing-service's affordability + dunning schedulers are machine-triggered (no end-user) and must compose an org's balance with only X-API-Key + org (no fake/sentinel x-user-id) — see next bullet.
- **Org teardown — `DELETE /internal/customers/by-org/:orgId`.** Part of the platform org cascade-teardown (api-service `DELETE /internal/admin/orgs/:orgId` orchestrates; this is its Stripe leg). Resolves `customers WHERE org_id = $1`, deletes each at Stripe via `stripe.customers.del(id)` using the **platform key** (`getPlatformStripe()` — single-account model, same as poller/back-fill/side-effects; per-org `resolveStripeKey` needs a userId teardown doesn't have), then **durably tombstones** silver. **Tombstone, never raw `DELETE FROM customers`:** a raw silver delete is resurrected on the next boot by `repairAllSilverFromBronze()`, which re-projects every `object_id` from the latest bronze event (a leftover `customer.created` / `api_snapshot.customer` event re-upserts the row). Instead it calls `recordApiSnapshot({ id, deleted: true, livemode }, "customer", orgId)` — the synthetic event's `created_stripe = now` dominates the projection's `ORDER BY created_stripe DESC`, so `projectSilverFromBronze` takes the `DeletedCustomer` branch (`db.delete(customers)`) and silver stays deleted across every re-projection; a later real `customer.deleted` webhook agrees. **Idempotent:** no customer row → 200, nothing deleted (no Stripe call). `resource_missing` from Stripe (already gone) is success and still tombstones. **Fail loud:** any other Stripe error propagates → non-2xx → caller retries. Order is delete-Stripe-then-tombstone so a crash mid-op re-runs cleanly. Scope is the customer only — PIs/checkout-sessions silver are NOT purged (they're historical records, not live billing entities, and have no `deleted` projection branch to tombstone against).
- **User-less org-scoped balance reads — `GET /internal/{customers,payment_intents,payment_methods}/by-org/:orgId`.** Back billing-service's balance composition (`computeBalance`) when the caller is a machine with no end-user — campaign-service's credit-affordability gate and the dunning scheduler are both machine-triggered. These mirror the `/v1` reads (`getCustomerByOrg` ← `GET /v1/customers?limit=1`; `sumSucceededTopupsForCustomer` ← `GET /v1/payment_intents`; `hasAttachedCardPm` ← `GET /v1/payment_methods`) in **passthrough Stripe shape** but key the org off the path and require **no x-user-id**. customers + payment_intents are pure DB-mirror reads (no Stripe call, no key). payment_methods is a live Stripe `paymentMethods.list` via the **platform key** (`getPlatformStripe()`, same single-account model as teardown — no user to resolve a per-org key against), customer resolved from the mirror (404 if none). payment_intents returns ALL the org's PIs with **no limit** (caller sums succeeded top-ups across the full set). **Why this surface exists:** stripe-service's global `requireIdentityHeaders` hard-requires x-user-id on every `/v1/*` route (Stripe key is resolved per-org-per-user there); billing was working around it by injecting a **zero-uuid x-user-id sentinel**, which the new affordability handler forgot → `400 Missing required header: x-user-id` → 502 → affordability fails OPEN (storm-protection inert). The fix is this user-less surface + billing dropping the sentinel on its balance path — NOT a fake user-id (stripe-service#77). No service-side balance composition — stripe-service has no business knowledge of callers; billing owns the `topups − usage` math.
- **The org's customers are OURS to enumerate, and rewriting the mapping is a user-less write.** `GET /internal/customers/by-org/:orgId/all` returns EVERY customer mirrored for the org (Stripe list), and `POST /internal/customers/:id/metadata` rewrites a customer's Stripe metadata with the platform key. Both exist because a machine caller reassigning an org's customers between tenants (billing's brand transfer) could otherwise only reach `GET /v1/customers?metadata[org_id]=` and `POST /v1/customers/:id` — identity-guarded routes it has no user for. **That caller was doing exactly the thing #77 removed and it was DEAD in prod:** it sent only a zero-uuid `x-user-id`, no `x-org-id`, so its very first call returned `400 Missing required header: x-org-id` (reproduced against prod 2026-08-29). The fix is the user-less surface, never the missing sentinel. **Why `/all` and not the existing singular read:** that one returns the ONE customer the 1:1 invariant promises, but orgs predating the idempotent `POST /v1/customers` (#92) can hold several — 4 of them in prod — and a transfer that lists only the newest silently strands the rest on the source org. **Why the `org_id` COLUMN and not a `metadata[org_id]` filter:** the column IS the mapping this service owns, it is what every other org-scoped read uses, and it stays right for a row whose Stripe metadata was never stamped (they agree in prod today — 0 of 129 rows differ). **The write is metadata-ONLY on purpose** — a user-less write surface stays as narrow as the need, and the need is the mapping; widen it when something needs more, not in advance. `metadata` is forwarded verbatim so Stripe's own semantics apply (keys MERGE; a key set to `""` is deleted). It re-mirrors through `recordApiSnapshot` resolving the org from the **updated** object, so a `metadata.org_id` rewrite — which is a tenant move — lands silver on the new owner in the same request instead of waiting for the next `customer.updated`. **Policy stays with the caller:** which customers are safe to move (billing's solo-brand rule) is business knowledge this service does not have and must not acquire.
- **Off-session invoiced charge — `POST /internal/invoices/by-org/:orgId`.** Lets an internal caller (billing-service) charge an org's Stripe customer OFF-SESSION for a top-up in a way that produces a **finalized, paid Stripe invoice** (hosted invoice + PDF, visible in the customer's billing-portal invoice list + Stripe invoice history, emailed like any Stripe invoice). Closes the auto-topup gap: interactive Checkout top-ups already invoice, but billing's automatic low-balance reload charges a bare off_session PaymentIntent with no invoice document. **Drives Stripe:** create draft invoice (`charge_automatically`, `auto_advance:false`, `pending_invoice_items_behavior:"exclude"`) → attach ONE line item bound to that invoice (`invoiceItems.create({ invoice })`) → `finalizeInvoice` → `pay({ off_session:true })`. Uses the **platform key** (`getPlatformStripe()`, single-account model — no end-user to resolve a per-org key against, same as teardown / balance reads). Body: `{ amount, currency, description, payment_method?, metadata? }` — `payment_method` (pm_…) is optional (else the customer default is used; prefer an explicit card PM since the default may be a Link/wallet PM Stripe refuses off_session). Stamps `metadata.org_id`. **Idempotent:** the mandatory `Idempotency-Key` header is derived per Stripe step (`:invoice`/`:item`/`:finalize`/`:pay`) so a retry replays each call from its Stripe idempotency record — no duplicate invoice, no double charge — regardless of where a prior attempt crashed. Missing header → 400 (cannot promise no-double-charge without a stable caller key). **Fail loud:** customer-less org → 404 (no Stripe call); any Stripe error (e.g. card declined → 402) propagates → non-2xx → caller retries. Returns the paid Stripe Invoice verbatim (with `payments` expanded). **Provenance + mirror freshness:** see the next bullet — after pay, the caller's metadata is stamped onto the resulting PaymentIntent and that PaymentIntent is snapshotted into silver, which also keeps billing's `payment_intents` top-up sum current so it can't re-trigger another auto-topup before the webhook lands.
- **Caller provenance on an invoiced charge must be stamped onto the PAYMENT — Stripe copies nothing between an Invoice and its PaymentIntent.** Consumers (billing-service) sum PaymentIntents, so "why did this payment happen" has to be readable there. Stripe's model gives you nothing for free in either direction: invoice `metadata` does NOT propagate to the PaymentIntent the invoice creates when paid, and on our API version that PaymentIntent has **no `invoice` field at all** (nor does the Charge) — the only link Stripe exposes is `invoice.payments[].payment.payment_intent`, and only when the pay call asks for `expand: ["payments"]`. Before the auto-reload moved to this route, every automatic charge was a bare PaymentIntent stamped by the caller (`{type:"auto_reload"}`, 84 of them Mar–May); after the move, 9 succeeded July payments mirrored with `metadata {}` and no way back to the invoice that explains them. So `POST /internal/invoices/by-org/:orgId` now resolves the PaymentIntent off the paid invoice, `paymentIntents.update`s it with `{...caller metadata, org_id, invoice_id}` **plus the caller's `description`** (keyed `<Idempotency-Key>:pi-provenance`), and mirrors THAT object via `recordApiSnapshot`. Helpers: `src/lib/invoice-provenance.ts`. **Both steps fail loud** — Stripe emits no event for a metadata update, so the snapshot is the ONLY path carrying provenance into silver (the `payment_intent.succeeded` webhook already landed with the empty metadata the PI was born with) and a swallowed failure would drop the caller's data permanently. Failing is safe *because* every Stripe step is idempotency-keyed: the caller retries the same logical top-up, each call replays from its Stripe idempotency record, no duplicate invoice and no double charge. **The `description` is the same problem one field over, and the customer-visible one.** Stripe labels the PaymentIntent an invoice creates with its own generic `"Payment for Invoice"`, regardless of how well the invoice is described — and a billing history rendered from payments (which is what ours is) shows that string. Verified in prod 2026-07-31: every invoiced auto top-up mirrored `description: "Payment for Invoice"`, sitting under checkout top-ups whose payment description is `null` (the dashboard labels those itself). The caller already writes a human description for the invoice and its line item (`"Distribute credit top-up"`); the fix carries that same string onto the PaymentIntent in the SAME idempotency-keyed update as the metadata, so it reaches the mirror and no consumer has to special-case Stripe's fallback. The key moved `:pi-metadata` → `:pi-provenance` because Stripe rejects a replayed idempotency key whose params changed. Checkout payments are untouched (they never go through this route). **Never invent provenance:** `scripts/backfill-invoice-provenance.ts` (`npm run backfill:invoice-provenance`, dry-run by default) reconciles historical blank rows by copying each invoice's OWN metadata onto its PaymentIntent, and skips loudly when a payment has no invoice or the invoice carries no metadata.
- **Verifying invoiced-charge behaviour in prod costs a real charge — there is no staging Stripe for this service.** Organic invoiced auto top-ups are sparse (roughly one every few days, plus a month-end sweep), so waiting for one is not a verification plan. Drive the route yourself: read `STRIPE_SERVICE_API_KEY` from `/root/distribute/env/stripe-service.env` on the host box (`ssh`), then POST to the service's public host with Python `urllib` and a clean `X-API-Key` (the api-registry `call_api` proxy mangles headers). The host was `stripe.distribute.you` under Railway; there is no `RAILWAY_PUBLIC_DOMAIN` var to read it from any more, so confirm the current hostname against the deploy config on the box rather than assuming it. Charge the SMALLEST amount (100 = $1) on the **platform owner's own org** — `f0420eb5-8f72-4f0a-a150-f473746df1e6` (`kevin.lourd@gmail.com`), the only owner-held org with a live card; the charge credits that same org, so it nets out. Every other `kevin@…` org either has zero PMs or a customer Stripe has since deleted (`No such customer: cus_…` from `GET /internal/payment_methods/by-org/:orgId` is the tell), and every org that DOES hold a card belongs to a real customer — never charge one to test. Read the result from the `payment_intents` mirror + the bronze `api_snapshot.payment_intent` event, not from the API response: the response proves Stripe accepted it, the mirror proves consumers will see it.
- **Money returned is a SEPARATE object, never a mutation of the payment — mirror the objects, sum on read.** Stripe's model is append-only: when money goes back out, the PaymentIntent stays `succeeded` at its full `amount_received` forever and the return lives on a **Refund** (`re_…`) or a **Dispute** (`dp_…`). So summing payments alone over-reports what an org still holds by exactly the amount refunded — the bug that left every refunded top-up as free spendable credit. The fix mirrors both objects as silver (`refunds`, `disputes`) through the same bronze→silver projection as everything else, and computes "returned" as a **query over current object state** (`src/lib/returned-amounts.ts`), never a stored accumulator. **Why a query, not a column:** it makes the awkward states correct *by construction* rather than by hand-maintained reconciliation — a **partial** refund contributes only its own `amount`; a refund that later **fails or is canceled** flips its own `status` and drops out of every sum on the next read with nothing to unwind; a **lost** dispute counts exactly like a refund, while an open or **won** one does not. Only `refund.status = 'succeeded'` and `dispute.status = 'lost'` are money gone. **Never delete, hide or mutate the original payment** — the mirror must stay reconcilable against Stripe, and the derived amounts are additive siblings.
- **`refunds` / `disputes` carry NO `org_id`.** The tenant lives on the referenced PaymentIntent row and is resolved by joining through it (`payment_intent`, falling back to `charge` ↔ `payment_intents.latest_charge` for the rare charge Stripe leaves PI-less). One home for the mapping means these rows can never drift out of sync with it, and a refund whose PaymentIntent is mirrored later starts attributing automatically — no `"unknown"` bucket, no ordering dependency. `projectSilverFromBronze(objectId, orgId)` therefore takes `orgId: string | null`; it **throws** if `null` arrives for an org-tenanted kind (fail loud — a mis-tenanted silver row is worse than an error).
- **Bronze events route on `data.object.object`, NEVER on the id prefix.** Stripe states an object's type authoritatively on the object itself, and that string is identical across payment rails. The id prefix is not: the very same Refund object is `re_…` when it reverses a card charge and **`pyr_…`** when it reverses a Link (or other non-card) payment — arriving as the same `charge.refund.updated`, with the same `object: "refund"`. `detectObjectKind(obj, objectId)` therefore reads `OBJECT_TYPE_TO_KIND[obj.object]` first and only falls back to `ID_PREFIX_TO_KIND` when a payload carries no `object` field at all. **An unroutable object is logged, never dropped in silence:** types we deliberately do not mirror live in an explicit `UNMIRRORED_OBJECT_TYPES` set and stay quiet; anything outside both maps emits a `console.warn` naming the object type, and the boot repair prints a per-type count of everything it walked past. **Why:** prefix routing silently dropped every Link refund from the mirror for months — `amount_returned` read 0, `amount_net` over-reported, and billing kept crediting orgs for money already returned (#100). A new payment rail must not be able to reintroduce that, so the discriminator is Stripe's own, and the unknown case is loud.
- **Four independent paths keep the money-returned mirrors fresh; none is load-bearing alone.** (1) **Webhooks/poll projection:** any payload whose `object` is `refund` / `dispute` projects with zero bespoke side-effect code, so `refund.*`, `charge.refund.updated` and `charge.dispute.*` all mirror regardless of id prefix. (2) **`charge.refunded` side-effect** (`src/lib/mirror-charge-refunds.ts`): that event's `data.object` is a **Charge**, and `charge.refunds` comes back `null` on our API version, so the projection alone can make nothing of it. `mirrorRefundsForChargeEvent` lists `refunds.list({ charge })` off Stripe and snapshots each Refund into bronze→silver. Keyed on the Charge, so a `py_…` Link charge yields its `pyr_…` refunds exactly as a `ch_…` card charge yields its `re_…` ones. This is what makes mirroring independent of **which** of the two subscribed events Stripe happens to deliver first — the second one is then an idempotent re-projection. (3) **The 5-min poller** reads Stripe `events.list` **unfiltered**, so a refund still lands within 5 minutes even if the webhook endpoint never subscribed to those event types. (4) **Boot back-fill** pages `refunds.list` / `disputes.list`, which is what reconciles history predating this code — required, because `events.list` cannot reach past Stripe's 30-day retention. Boot also re-projects every bronze object (`repairAllSilverFromBronze`), so an event we stored but could not route at the time is recovered the moment routing improves — that is the reconciliation path, not a one-off script.
- **`GET /internal/payment_summary/by-org/:orgId` — what came in, what went back, what's still real.** Per-currency `amount_received` / `amount_refunded` / `amount_disputed_lost` / `amount_returned` / `amount_net`, DB-mirror only (no Stripe call), X-API-Key + org in the path, **no end-user identity** — billing's balance path is machine-triggered (affordability gate, dunning scheduler) and has no user to resolve. `amount_received` uses **byte-identical predicate to billing's own top-up sum** (`status === "succeeded"` AND numeric `amount_received`), which is what guarantees `amount_net === amount_received` for an org with no refunds. Currencies are **never merged** into a scalar. An org with nothing mirrored gets `totals: []` and `customer: null` — not a fabricated zero row. **This is Stripe money movement ONLY, NOT a credit balance:** promo grants and usage stay billing-service's business, so the "no service-side balance composition" rule still holds — we expose the truth, billing does the arithmetic.
- **`?as_of=<unix seconds>` on the payment summary answers the same question AS OF a moment, bounding BOTH sides.** Consumers need "what had this org paid, net of returns, at date T" to grandfather an offer against a launch instant, and billing was computing it itself by reading `/internal/payment_intents/by-org/:orgId` and filtering each PaymentIntent on its own `created` — vendor-shape coupling on the last stretch of the money path that still had it. The bound applies to payments AND to returns (`created_stripe` strictly `<` the instant, on all three of `payment_intents` / `refunds` / `disputes`), so the reply is the one this endpoint would itself have given then, and `as_of` at the current second is byte-identical to the unbounded reply. **This is the same time attribution `/public/stats/billing` already uses:** a return belongs to the moment it HAPPENED and is never back-dated onto the payment it reverses, because back-dating rewrites a figure a consumer has already read. ⚠️ **It therefore differs from billing's pre-existing computation**, which bounded the payment but subtracted every return ever — under that reading a pre-launch payment refunded after launch is excluded from the grandfather; under this one it counts, because at T the money had been paid and had not come back. The bound is **exclusive**, so a launch instant splits history cleanly (a payment made at T itself is post-launch). An object with **no `created_stripe`** cannot be placed in time and is excluded from a bounded read (`<` is NULL for a null column, so it falls out of the predicate rather than being special-cased) while an unbounded read still counts it — one rule for payments and returns alike, so the two sides of `amount_net` are never drawn from different populations. `customer` is identity, not a money figure, and is never bounded. **`as_of` is echoed back** (null when absent) so a caller can distinguish a deploy that applied the bound from one that predates it — without the echo those two responses are identical and the older one silently over-counts. A malformed `as_of` is a **400, never an ignored filter**: dropping the bound would answer a different question and read as a correct answer.
- **Per-payment returned amounts ride along on the PaymentIntent reads.** `GET /internal/payment_intents/by-org/:orgId` (which backs BOTH billing's top-up sum and, via api-service `GET /v1/billing/payments`, the dashboard's payment history) plus `GET /v1/payment_intents` list/retrieve return the verbatim Stripe object **plus** `amount_refunded` / `amount_disputed_lost` / `amount_returned`. This is a deliberate, documented exception to strict Stripe-shape passthrough: Stripe's PaymentIntent has no refund field at all (it lives on the Charge, and even `charge.amount_refunded` **omits a lost dispute**), so there is no Stripe-native field that tells the truth here. `raw_json` stays untouched. All three PI read surfaces carry the fields so one can never show a payment as plain `succeeded` while another shows it refunded.
- **`GET /public/stats/billing` publishes GROSS and NET side by side — a consumer must never have to re-derive credited from raw payments.** The platform-wide surface carries `total_paid_cents` (gross charges, **meaning unchanged** — this is the revenue figure, and accounting reports revenue gross), `total_refunded_cents` / `total_disputed_lost_cents` / `total_returned_cents`, and `total_net_cents` = gross − returned, which is what a consumer reports as **credited**. Every `monthly_growth` / `weekly_growth` bucket carries the same five figures, so a time series cannot silently mean something different from the all-time total. Returns reuse the per-payment rule verbatim (`refund.status = 'succeeded'`, `dispute.status = 'lost'`, attributed to a mirrored PaymentIntent through `payment_intent` with a `charge` ↔ `latest_charge` fallback), which is what makes `total_net_cents` **exactly the sum of every org's `amount_net`** from `GET /internal/payment_summary/by-org/:orgId` — the platform figure and the per-org ones can no longer contradict each other. Currencies are summed together here, as the pre-existing gross total already did; per-currency truth lives on the per-org summary, which never merges them. Implementation: `src/lib/platform-billing-stats.ts` (grouped by (month, week) in SQL over the refund/dispute rows themselves, never the join product, so an object matching on both keys counts once).
- **Time attribution: a return lands in the period it HAPPENED, never back-dated to the payment it reverses.** A refund almost always falls in a later period than its payment, so the choice is forced and is documented on the endpoint: back-dating would retroactively rewrite a bucket a consumer has already read and reported, and this mirror is append-only like Stripe's own ledger. The deliberate consequence is that a period whose refunds exceed its payments reports a **negative `net_cents`** — that is the honest reading, not a bug. Both attributions preserve `sum(buckets) === all-time total`; only this one leaves history immutable.
- **org_id stamping.** On every `POST /v1/{customers,checkout/sessions,payment_intents}`, stripe-service stamps `metadata.org_id = <x-org-id>` so webhook events route back to the right tenant via `event.data.object.metadata.org_id`.
- **Webhook + 5-min poll sync.** Webhooks are primary. A background `setInterval(5min)` pulls Stripe `events.list` since the cursor stored in `event_sync_cursor` and processes any missed events. Both paths share `processEvent()` which is idempotent via `ON CONFLICT DO NOTHING` on `events.id`.
- **Default-PM auto-promotion.** Stripe Checkout attaches the chosen PM to the customer but does NOT set it as `invoice_settings.default_payment_method`. Without a default, billing-service `deriveHasPaymentMethod` returns false (dashboard "No card") and off_session PaymentIntents fail with `requires_payment_method`. `processEvent()` calls `promoteDefaultPaymentMethod(event, stripe)` after the mirror upsert for `checkout.session.completed` (modes `payment`/`setup`) and `setup_intent.succeeded`. It retrieves the customer; if a default PM is already set, it's a no-op. Otherwise it derives the PM (PI/SI lookup for checkout, payload for SI), calls `customers.update(id, { invoice_settings: { default_payment_method: pm } })`, and re-mirrors via `upsertCustomer`. Errors propagate so the webhook returns 5xx and Stripe retries. Uses the platform Stripe key (same single-account model as the poller + back-fill). Forward-only — no historical back-fill of older customers. **Note:** the promoted PM is whatever the customer used to complete checkout, which may be a Stripe Link / wallet PM. Stripe refuses to charge Link / wallet PMs in off_session mode via the `invoice_settings.default_payment_method` fallback ("You cannot confirm this PaymentIntent because it's missing a payment method"). Callers that need off_session must NOT rely on the default-PM fallback — instead list the customer's PMs via `GET /v1/payment_methods?customer=&type=card` and pass `payment_method` explicit on the PI create call.
- **`GET /v1/payment_methods` is a live Stripe passthrough.** No mirror table. Calls `stripe.paymentMethods.list({ customer, type? })` after verifying the customer exists in the caller's org mirror (prevents cross-org PM enumeration via guessed cus_xxx IDs). Live-Stripe (not mirror) because PMs detach / attach without always emitting `customer.updated` events, so any local cache would drift. Callers that need an off_session-capable card PM should query this endpoint and pick the first card-type result rather than reading `customer.invoice_settings.default_payment_method` (which may be a Link / wallet PM Stripe refuses for off_session).
- **Stripe-fee declaration to runs-service.** On `charge.succeeded` / `charge.refunded` / `charge.dispute.created` / `payout.failed`, `processEvent()` calls `declareFeesForEvent(event, stripe)` after the mirror upsert. For each fee-bearing balance-transaction referenced by the event, it retrieves the BT (via the platform Stripe key), resolves the owning org via `customers.org_id`, reads `keySource` from key-service `GET /keys/stripe/source`, then POSTs to runs-service: `POST /v1/platform-runs` (taskName = the event type, x-org-id header set when an org is attributable), `POST /v1/platform-runs/:id/costs` (`costName` ∈ {`stripe-processing-fee`, `stripe-refund-fee`, `stripe-dispute-fee`, `stripe-payout-failure-fee`}, `costSource` from keySource for org-attributable events, `platform` for `payout.failed` and customer-less charges, `quantity` = `balance_transaction.fee` in cents, `status: actual`), then `PATCH /v1/platform-runs/:id` to `completed`. The Stripe `balance_transaction.id` is passed as `idempotencyKey` on both the run and the cost so Stripe webhook redelivery is safe (runs-service returns the existing rows on the second call). Errors propagate so the webhook returns 5xx and Stripe retries; on cost-write failure the run is best-effort patched to `failed` before re-throw. **costName must match the kebab-case strings registered in costs-service** — `stripe.processing_fee` etc. will 422 with "Unknown cost name". The 2× cost-risk-multiplier applied by costs-service is intentional platform-wide convention; not a stripe-service concern. Fee amount is read from `balance_transaction.fee` so non-charge events (refund/payout/dispute) only declare when Stripe populates the fee field (best-effort capture for those classes).
- **A lost payment method is a staff notification, not a mirror.** There is no "remove card" control in our product: the customer removes it inside Stripe's own billing portal, so no write path of ours can observe it. The only place the fact exists is bronze, which already receives `payment_method.detached` from the webhook and from the unfiltered 5-minute poll. `notifyPaymentMethodRemoved` reads that event and emails staff via transactional-email-service under the event key **`payment_method_removed`** (frozen byte-for-byte with that service's staff-routing table and its template name — a drift there mails the customer instead of staff). Payment methods stay **unmirrored**: nothing new is stored, `UNMIRRORED_OBJECT_TYPES` still lists `payment_method`, and the projection is untouched. **Attribution reads `previous_attributes`, not the object:** Stripe sets `data.object.customer` to `null` on a detach and states the previous owner only in `data.previous_attributes.customer` (verified on the live event `evt_1TzQD1EnlXMXdaZao55dx2VF`, 2026-07-31). **Every detach notifies** — the mail carries the count of the customer's remaining **card-type** payment methods (auto-paginated, card-only because Stripe refuses Link and wallet PMs off_session), and zero is what makes it urgent: automatic top-up can no longer run. **Three silences, all logged:** a customer that maps to no org of ours, a customer Stripe reports `deleted: true`, and a customer Stripe no longer has at all (`resource_missing`). The last two are org teardown, which detaches every card the org held and must not produce a burst of mail about an org that no longer exists. **One detach is one email** by construction — `processEvent` runs side-effects only when the bronze insert was new, so webhook delivery, redelivery and the poller all collapse on the same `evt_…`, and `repairAllSilverFromBronze` runs no side-effects at boot. **It can never fail the webhook:** Stripe retries a non-2xx, so an email service that is down would become an endless redelivery loop. The notifier therefore swallows everything and returns a boolean, and it takes a Stripe *resolver* rather than a client so that even resolving the platform key is inside the guard. This is the one side-effect here that does not fail loud; every other one still does.
- **Boot-time historical back-fill.** On every boot, `backfillHistorical()` runs as a fire-and-forget background task fired right after `app.listen()`. Iterates `customers.list`, `paymentIntents.list`, `checkout.sessions.list`, then `refunds.list` and `disputes.list` globally (refunds/disputes last, after the PaymentIntents they attribute through). Routes each object to its tenant via `metadata.org_id`, then falls back to the local `customers` mirror's `org_id` for PaymentIntents and CheckoutSessions whose own metadata lacks `org_id` (PIs created via Checkout sessions don't inherit the session's metadata, so the customer lookup is the only recoverable source). Same `resolveOrgId(metadataOrgId, customerId)` helper in `event-processor.ts` is used by webhook + poll-driven upserts so the bug class cannot recur. Only stamps `"unknown"` when both sources are empty. Idempotent via `ON CONFLICT DO UPDATE` so re-runs refresh `raw_json` / status. Failure is logged via `console.error` but does NOT crash the service — the port is bound first so callers never get ECONNREFUSED during the back-fill window. Recovers Feb→Apr 2026 history that the 30-day events.list cursor cannot reach.
- **`customer.balance` is polluted — stripped on write.** Pre-#104 (billing-service), every usage tick wrote a `usage_applied` CBT into Stripe via `stripe.customers.createBalanceTransaction(...)`. Stripe's `customer.balance` is the running sum of those CBTs plus real top-up credits, so it no longer represents a pure prepaid balance for any org with pre-#104 history. `upsertCustomer()` strips `raw_json.balance` before persisting; no stripe-service response, mirror table, or back-fill exposes the field. Downstream consumers must compute credit balance from `payment_intents.amount_received` + their own promo ledger, NOT from `customer.balance`.
- **No `customer_balance_transactions` exposure.** Mirror table + `GET /v1/balance_transactions` route + webhook handler for `customer_balance_transaction.*` events are all removed. Same legacy-pollution rationale: individual CBTs cannot be cleanly partitioned into "real credit" vs "legacy usage_applied" without unreliable type heuristics. Drop the surface entirely. If a downstream service needs credit history, source it from its own ledger.
- **No service-side reload dedupe.** Stripe-service has no in-flight lock, no customer-scope coalesce, no gap-fill logic. Clients (billing-service) inspect in-flight PaymentIntents via `GET /v1/payment_intents?customer=cus_X` and own the business logic for "don't trigger reload too often".
- **Idempotency-Key forwarding.** If the caller sends an `Idempotency-Key` header, it's forwarded verbatim to the Stripe SDK call. Otherwise the SDK is called without one.
- **Reads.** Single-object GET = DB-first + Stripe fallback when row missing. List = DB-only (no live Stripe fetch). Webhook + poll keep DB fresh.
- **Auth.** `X-API-Key` mandatory on all non-webhook, non-public routes (including `/internal/*`). `x-org-id` + `x-user-id` mandatory on `/v1/*` because Stripe key resolution is per-org; `/internal/*` is exempt (keys the org off the path). `x-brand-id`, `x-campaign-id`, `x-workflow-slug` optional — logged to `api_call_log` when present.
- **Multi-tenant Stripe key.** `resolveStripeKey(orgId, userId)` calls key-service `GET /keys/stripe/decrypt`. Per-request Stripe client (`makeStripeClient(key)`), no shared SDK instance.

## Revolut — the second acquirer (mirror-only, dark)

**Nothing routes to it and no consumer reads it.** The tables fill, and that is
all. billing-service does not know Revolut exists and must not learn.

- **src/lib/revolut-client.ts** — Merchant API client. Secret key from key-service platform provider `revolut` (single merchant account, same model as the Stripe platform key). `Revolut-Api-Version` is PINNED: the API is versioned by date and old versions vanish (`2023-09-01` already 404s), so leaving it unset would let every response shape drift under the projector without a deploy.
- **src/lib/revolut-processor.ts** — bronze → silver, same contract as the Stripe side: nothing writes silver directly, and the projection reads the LATEST snapshot rather than whatever arrived last. Ordering key is Revolut's own `updated_at` (monotonic per object), playing the role `event.created` plays for Stripe.
- **src/routes/revolut-webhooks.ts** — `POST /v1/revolut/webhooks`. Signature-verified, exempt from BOTH `serviceAuth` and `requireIdentityHeaders`.
- **src/lib/revolut-poller.ts** — 5-min reconciliation over a 24h window + `backfillRevolutHistory()` at boot (fire-and-forget after `listen()`).

### Key patterns (verified against a real production transaction, 2026-08-30 — not against docs)

- **One collection, discriminated by `type`.** `GET /orders` returns payments AND refunds. A refund is a TOP-LEVEL order of `type: "refund"` carrying `related_order_id` — the direct analogue of Stripe's `refund.payment_intent`. **There is no refund array nested on the payment, and no `/refunds` endpoint** (`GET /refunds` → `401 code:2000`, which means "not on this surface", NOT "not authorized"). So money-returned needs no special projector: it is `type='refund' AND state='completed'`, the same "one row per return keyed by its own id, summed over current state" contract the Stripe mirror already guarantees.
- **Route on `type`, never on the id.** Revolut ids are **bare UUIDs with no prefix** and there is **no `object` field**. Same rule as the Stripe side (`data.object.object`), different field name. An id prefix would be no help at all here — there isn't one.
- **The webhook body is a TRIGGER, never the record.** A delivery tells us WHICH order changed; we then `GET` that order and store what Revolut authoritatively says. Two consequences, both deliberate: the mirror does not depend on any webhook payload shape (still unobserved — nothing has been delivered yet), and a replayed or reordered delivery cannot write a stale state.
- **Mirroring a refund re-reads its parent.** `refunded_amount` only ever moves on the payment, so a refund we just learned about leaves the payment stale until it is re-read too.
- **⚠️ `GET /orders` is a SUMMARY, and the detail-only rule is STRUCTURAL because it cannot be sniffed.** The list omits `payments` and `refunded_amount` — the fee, the settled amount, and how much came back — so storing one would let a poll blank those fields on an order already mirrored correctly. The obvious defence, checking the payload for those keys, is **wrong**: a cancelled or never-paid order's DETAIL has neither field either, so it is byte-identical in shape to a list entry. That guard shipped, and in production it rejected a real `ORDER_CANCELLED` delivery and 500'd it back to Revolut — the exact way an endpoint gets disabled. There is no discriminator in the data, only provenance. So `recordRevolutObject` is **not exported**: the only way an order reaches bronze is `mirrorOrderById`, which fetches it itself. The list is used for discovery of ids and nothing else.
- **Only ORDER_* webhook events exist — and that is ENOUGH, because a refund IS an order.** Verified at registration by iteratively dropping what the API rejected: `PAYMENT_COMPLETED`, `PAYMENT_DECLINED`, `REFUND_COMPLETED` and `REFUND_FAILED` are all unsupported. It is tempting to read that as "there is no refund webhook, so refunds are poller-only" — **that is wrong, and the mirror disproves it**: 7 refund objects arrived with `source='webhook'`. Refunds are orders, so the `ORDER_*` subscription delivers them exactly as it delivers payments. There is **no freshness asymmetry between the two halves of money-returned**; both have webhook and poll. Do not reintroduce one from the event-name list alone — check `revolut_object_snapshots.source` joined to `revolut_orders.type`, which answers it directly.
- **A refund's org is JOINED through `related_order_id`, never copied onto the row.** Revolut mints a refund as its own order with NO metadata, so it cannot answer for itself. Same rule as the Stripe `refunds`/`disputes` tables, which carry no `org_id` either — and here it is not just tidiness: the back-fill walks NEWEST-FIRST, so a refund is mirrored BEFORE the payment it belongs to, and a copied tenant is written null forever with nothing to heal it. Observed in production on the first deploy: three refunds landed with a null org while their payment carried one. `revolutOrgIdOf` therefore reads the order's own metadata and nothing else.
- **Fees live on the payment, not on a separate object.** `payments[].fees[]` is an ARRAY of typed entries, so `feeAmountOf` SUMS them rather than reading `fees[0]` — taking the first would silently under-report the moment Revolut adds a second kind. Null for an unsettled order, which is not a fee of zero.
- **A refund needs SETTLED merchant funds.** Stripe refunds against a pending balance and will go negative; Revolut returns `400 insufficient_funds` until the money has settled. A refund can therefore fail for a reason that has nothing to do with the payment, and each failed attempt creates a real refund order at `state: "failed"` — which is exactly the "a refund that later fails drops out of every sum" case, and it works by construction.
- **Bronze is keyed on a CONTENT HASH, not a vendor event id.** All four freshness paths legitimately fetch the same object; hashing the payload means an identical re-read collapses onto the row already there instead of inflating the ledger. It also needs no assumption about which id or timestamp field a shape we have not seen yet will carry.
- **No dispute silver table, on purpose.** `GET /disputes` IS listable (unlike refunds) but has only ever returned an empty list, so no dispute payload has been observed. Disputes are captured in bronze and will be projected when a real one exists. Typed columns for an unobserved shape would be guesswork.
- ⚠️ **The fee premise is UNMEASURED.** The one real transaction settled `472` of `500` — a 28¢ acquiring fee, 5.6% — but it was paid with `revolut_pay_account`, NOT a card. That says nothing about the cheap EEA card rate the second acquirer was chosen for. Do not quote a Revolut-vs-Stripe comparison from it.
- **Webhook exemptions are per-path and easy to miss.** `/v1/revolut/webhooks` does NOT match the `/v1/webhooks` prefix that exempts Stripe, so it needs its OWN entry in `serviceAuth` AND `identityHeaders`. Without both, every delivery 4xxs — and a webhook that keeps failing gets the endpoint **disabled by the sender**, silently.

### Routing an org to Revolut

- **The acquirer pin lives HERE, and billing never names a vendor.** This service already owns the other half of the same fact — which KEY charges an org, resolved per-org from key-service — so which acquirer that key belongs to is our business too. `org_acquirers` is absent-means-Stripe, so every org that predates it keeps its behaviour with no backfill and a lookup miss can never reroute money. A row we cannot READ throws rather than falling back: charging on the default would put the money through the wrong acquirer while the customer's saved card sits on the other one.
- **Re-pinning an org that already has a customer on the other acquirer is REFUSED.** A saved card lives with one acquirer and cannot move. Flipping the pin would leave the org uncharge-able while its dashboard still shows a card on file — a decline nobody can explain.
- **The route billing already calls DISPATCHES on the acquirer.** `POST /internal/invoices/by-org/:orgId` resolves the pin first: a Stripe org takes the unchanged invoice path and gets its verbatim Invoice, an org on an acquirer with no invoice object gets the neutral charge result instead. The shape differs **because the capability differs**, and saying so is the point — a caller that needs the document checks for it rather than being handed a fabricated one. The dispatch lives here rather than in the caller because the caller asked to take money and never named a vendor.
- **`POST /internal/charges/by-org/:orgId` is the forward-looking neutral charge.** The caller states an amount and a reason and never names an acquirer. `hosted_document_url` is null for an acquirer with no invoice object — Revolut has none — and null means "this acquirer does not produce one", never "it failed". A Stripe org gets a **409 pointing at the invoice route**, because that route produces the finalized invoice + PDF this one cannot, and silently downgrading a Stripe org to a document-less charge would lose a customer-visible artifact.
- **The payment summary spans BOTH acquirers, and that is what makes a switch safe.** An org's money is its money whichever acquirer took it. Without this, moving an org to a second acquirer makes its payments invisible to every balance that reads this endpoint: **it would pay and its balance would not move.** Revolut money in is `type='payment' AND state='completed'`; money out is `type='refund' AND state='completed'`, attributed by joining the refund to its parent through `related_order_id`.
- **Charging via Revolut = create order, then `POST /orders/{id}/payments` with `saved_payment_method: {type, id}`.** Established against the live API, not docs: the endpoint answers `400 Either 'payment_method' or 'saved_payment_method' must be set`, and both `type` and a UUID `id` are required.
- **The saved-method list is read LIVE on every charge, never cached.** Revolut invalidates merchant-initiated eligibility once the customer UPDATES their card — no event, no error, until the charge fails. Reading live puts the refusal here, where the reason is legible, instead of at the acquirer.
- **The charge mirrors the order in a `finally`, including when the pay call THROWS.** A declined charge is a real state; leaving it unmirrored makes a failure indistinguishable from a charge that never ran.

## Out of scope (Phase 2)

Products, prices, subscriptions, invoices (Stripe objects not currently used by Distribute callers). Charges are still not mirrored as a table — refunds and disputes both carry `payment_intent`, so the Charge adds no attribution we need. Push-style webhook fan-out to downstream services. Reload-specific business endpoints (those live in billing-service). `customer.balance` and `customer_balance_transactions` (intentionally removed, see key patterns).
